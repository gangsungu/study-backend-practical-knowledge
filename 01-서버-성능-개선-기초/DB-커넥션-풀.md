## DB 커넥션 풀

DB 연동이 느린 이유가 꼭 쿼리 때문만은 아니다. **연결을 만들고 끊는 시간**이 쿼리 실행보다 길 수도 있다.
커넥션 풀은 연결을 미리 만들어두고 재사용해서 이 비용을 없애지만, **크기와 대기 시간을 어떻게 잡느냐**에 따라 처리량과 응답 시간이 크게 달라진다.

### DB 연결 비용
+ DB를 사용하려면 3단계를 거침
    - DB에 연결
    - 쿼리 실행
    - 사용이 끝나면 연결 종료
+ 서버와 DB는 네트워크로 연결되며, 상황에 따라 연결을 생성하고 종료하는 데만 **0.5초에서 1초 이상** 걸리기도 함
+ 연결 시간이 그보다 훨씬 짧더라도 비중은 무시할 수 없음
    - 예를 들어 실행 시간이 10ms인 쿼리를 위해 연결과 종료에 50ms가 걸리면, 전체 처리 시간의 **80% 이상**이 연결과 종료에 쓰임

### 커넥션 풀
+ DB 커넥션을 **미리 생성해 풀에 보관하고 재사용**하는 방식
    - 요청마다 연결을 새로 만들고 끊는 비용이 사라짐
+ 다양한 설정을 제공하며, 그중 중요한 설정은 아래 세 가지
    - 커넥션 풀 크기
    - 커넥션 대기 시간
    - 커넥션 유지 시간

### 커넥션 풀 크기
+ 풀에 미리 생성해둘 커넥션 개수 (최소 크기, 최대 크기로 나뉘기도 함)
    - **가장 중요한 설정**
+ 다음 상황을 가정
    - 커넥션 풀 크기는 5
    - 한 요청의 쿼리 실행 시간은 1초
    - 계산을 쉽게 하기 위해 데이터 전송 시간은 무시
    - 6개 요청이 동시에 들어오면 5개는 바로 커넥션을 가져가지만, **6번째 요청은 1초 대기**
+ 커넥션을 얻기 위한 대기 시간을 줄이려면 전체 응답 시간과 TPS를 함께 고려해야 함

| 커넥션 풀 크기 | 쿼리 실행 시간 | TPS |
|:-:|:-:|:-:|
| 5 | 0.1초 | 50 |
| 5 | 0.5초 | 10 |

+ 동시에 50개 요청이 들어온다면
    - 위쪽은 50개 요청이 **모두 1초 안에** 처리됨
        + 바로 커넥션을 얻는 요청도, 대기하는 요청도 있지만 대기는 최대 0.9초
    - 아래쪽은 1초에 10개만 처리할 수 있어 전체 처리에 **5초**가 걸림
        + 0.5초 만에 끝나는 요청도 있지만, 어떤 요청은 커넥션을 얻기 위해 4.5초까지 대기
+ 커넥션 풀 크기를 늘리면 처리량을 높일 수 있음
    - 단, DB 서버의 CPU 사용량이 80~90%에 육박한 상황에서 풀을 늘리면 DB 부하가 더 커져 **쿼리 실행 시간이 급격히 증가**할 수 있음

### 커넥션 대기 시간
+ 풀에 사용할 수 있는 커넥션이 없을 때, 커넥션을 얻기 위해 **대기할 수 있는 최대 시간**
    - 지정된 시간 안에 커넥션을 구하지 못하면 DB 연결 실패 에러 발생
    - 대기하는 시간만큼 응답 시간도 길어짐
+ 대기 시간을 짧게 잡으면, 풀이 모두 사용 중일 때 사용자에게 **빠르게 에러를 응답**할 수 있음
    - 에러 응답이 부정적으로 보일 수 있지만, 커넥션을 기다리느라 오래 대기하는 것보다 나음
    - 서버 부하가 계속 쌓이는 것을 막는 효과도 있음

### 커넥션 유지 시간
+ 최대 유휴 시간
    - 사용하지 않는 커넥션을 풀에 유지할 수 있는 최대 시간
    - 30분으로 설정하면, 30분 이상 사용하지 않은 커넥션은 종료되어 풀에서 제거됨
+ 유효성 검사
    - 커넥션이 정상적으로 사용 가능한 상태인지 확인하는 절차
    - 일부 커넥션 풀은 검사를 위해 실제 쿼리를 실행하기도 함 (`SELECT 1 FROM DUAL`, `SELECT 1` 등)
+ 최대 유지 시간
    - 커넥션을 유지할 수 있는 최대 시간
    - 4시간으로 설정하면, 유효한 커넥션이어도 4시간이 되면 종료함

### 유지 시간 설정이 필요한 이유
+ 커넥션은 서버만 관리하는 게 아님. **DB나 중간 네트워크 장비가 먼저 끊을 수 있음**
    - DB는 일정 시간 쓰이지 않은 연결을 스스로 끊음 (MySQL `wait_timeout`, 기본 8시간)
    - 방화벽·로드밸런서도 유휴 연결을 정리함
+ 풀은 이 사실을 모른 채 끊긴 커넥션을 보관하고 있다가 요청에 내줄 수 있음
    - 그 요청은 쿼리 실행 시점에 에러가 남
+ 그래서
    - **유효성 검사**로 커넥션을 내주기 전에 살아 있는지 확인하고
    - **최대 유지 시간**을 DB·네트워크 장비의 제한보다 **짧게** 잡아, 상대가 끊기 전에 풀이 먼저 정리하게 함

### HikariCP 설정 이름
+ Spring Boot의 기본 커넥션 풀은 HikariCP
    - 설정은 `spring.datasource.hikari.*`로 지정

| 노트의 개념 | HikariCP 설정 | 기본값 |
|------------|--------------|:------:|
| 커넥션 풀 크기 | `maximumPoolSize` | 10 |
| 커넥션 풀 최소 크기 | `minimumIdle` | `maximumPoolSize`와 같음 |
| 커넥션 대기 시간 | `connectionTimeout` | 30초 |
| 최대 유휴 시간 | `idleTimeout` | 10분 |
| 최대 유지 시간 | `maxLifetime` | 30분 |

+ `minimumIdle`을 따로 지정하지 않으면 풀 크기가 고정됨 (HikariCP가 권장하는 방식)
    - `idleTimeout`은 `minimumIdle`이 `maximumPoolSize`보다 작을 때만 동작
+ 유효성 검사는 기본적으로 JDBC4의 `Connection.isValid()`를 사용
    - `SELECT 1` 같은 검사 쿼리(`connectionTestQuery`)는 이를 지원하지 않는 오래된 드라이버에서만 지정

### 자주 하는 착각
+ "DB가 느린 건 쿼리가 느려서다"
    - 연결을 만들고 끊는 비용이 쿼리 실행보다 클 수 있음. 커넥션 풀을 쓰는 이유
+ "커넥션 풀은 클수록 좋다"
    - DB CPU가 이미 높으면 풀을 늘릴수록 DB 부하가 커져 **쿼리 실행 시간이 급격히 늘어남**. 서버 여러 대라면 `서버 수 × 풀 크기`가 DB 한계를 넘을 수도 있음
+ "커넥션 대기 시간은 길게 잡을수록 안전하다"
    - 대기하는 만큼 응답 시간이 늘고, 대기 중인 요청이 쌓여 서버 부하도 커짐. **짧게 잡고 빨리 에러를 응답**하는 편이 나음
+ "풀에 있는 커넥션은 항상 쓸 수 있다"
    - DB나 네트워크 장비가 먼저 끊었을 수 있음. 유효성 검사와 최대 유지 시간이 필요한 이유
