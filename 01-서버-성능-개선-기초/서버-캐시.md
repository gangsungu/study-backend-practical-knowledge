## 서버 캐시

DB를 수직 확장하면 비용이 많이 들고, 수평 확장하면 처리량은 늘어도 **쿼리 실행 시간이 크게 줄지는 않는다**.
이럴 때 자주 조회되는 데이터를 캐시에 두면 DB를 거치지 않고 응답할 수 있다.
다만 캐시는 **무엇을 얼마나 담을지**, **원본이 바뀌면 언제 지울지**를 함께 정해야 하는 도구다.

### 캐시가 필요한 이유
+ 캐시에 데이터를 저장해두면, 같은 데이터를 다시 요청할 때 DB가 아닌 **캐시에서 읽어 응답**할 수 있음
+ 데이터 특성에 따라 차이는 있지만, 일반적으로 캐시는 DB보다 읽는 속도가 빠름
    - 자주 조회되는 데이터를 캐시에 저장하면 응답 시간을 줄일 수 있음
+ 캐시는 **키-값** 형태로 데이터를 저장
    - 저장 대상에 맞는 캐시 키를 골라야 하고, **키가 겹치지 않도록** 주의해야 함
    - 보통 **데이터 종류를 접두사로** 붙여 구분함
        + 회원 1번과 상품 1번을 모두 `1`로 저장하면 서로 덮어씀
        + `user:1`, `product:1`처럼 쓰면 겹치지 않음
        + 조건이 붙는 조회는 조건까지 키에 넣음 (`product:list:category=3:page=1`)

### 적중률
+ 캐시가 얼마나 효율적으로 쓰이는지 판단하는 지표
    - `적중률 = 캐시에 데이터가 존재한 건수 / 캐시에서 조회를 시도한 건수`
    - 100번 조회해서 87번 데이터가 있었다면 적중률은 87%
+ 적중률이 높을수록 DB 연동이 줄어 **응답 시간 감소, 처리량 증가, DB 부하 감소**로 이어짐
+ 적중률을 높이는 가장 좋은 방법은 캐시에 최대한 많은 데이터를 저장하는 것
    - 하지만 캐시는 메모리를 사용하므로 모든 데이터를 저장할 수는 없음
    - 캐시가 가득 찬 상태에서 새 데이터를 저장하려면 **기존 데이터를 제거**해야 함

### 삭제 규칙
+ 캐시가 가득 찼을 때 제거할 대상을 고르는 규칙

| 규칙 | 제거 대상 |
|------|----------|
| LRU (Least Recently Used) | 가장 오래전에 사용된 데이터 |
| LFU (Least Frequently Used) | 가장 적게 사용된 데이터 |
| FIFO (First In First Out) | 가장 먼저 추가된 데이터 |

+ 가득 찼을 때뿐 아니라 **TTL(Time To Live)**이라는 유효 시간을 정해 데이터를 삭제하기도 함

### 로컬 캐시와 리모트 캐시
+ 로컬 캐시
    - 서버 프로세스와 **같은 메모리**를 캐시 저장소로 사용하는 인-메모리 캐시
    - 장점
        + 같은 메모리 공간을 쓰므로 속도가 빠름
        + 별도의 외부 연동이 필요 없어 구조를 단순하게 유지할 수 있음
    - 단점
        + 같은 메모리 공간을 쓰므로 저장할 수 있는 데이터 크기에 제한이 있음
        + 서버 프로세스를 재시작하면 캐시 데이터가 모두 사라져 일시적으로 적중률이 떨어짐
+ 리모트 캐시
    - **별도의 프로세스**를 캐시 저장소로 사용
    - 로컬 캐시와 정반대의 장단점을 가짐

| 구분 | 로컬 캐시 | 리모트 캐시 |
|------|----------|------------|
| 대표 구현체 | Caffeine, Ehcache | Redis, Memcached |
| 저장 위치 | 서버 프로세스 메모리 | 별도 프로세스 |
| 속도 | 빠름 | 네트워크를 거쳐 상대적으로 느림 |
| 구조 | 단순 | 외부 연동이 필요해 복잡 |
| 저장 크기 | 서버 메모리에 제한됨 | 상대적으로 제한이 적음 |
| 서버 재시작 | 캐시가 사라짐 | 영향 없음 |

### 캐시 사전 적재
+ 트래픽이 **순간적으로 급증**하는 패턴이라면 캐시에 데이터를 미리 저장해두는 방법도 고려할 수 있음
+ 가상 사례
    - 앱 사용자는 300만 명
    - 매달 정해진 날에 이달의 요금 정보를 제공하고, 그날 전체 회원에게 요금 안내 푸시 알림을 발송
    - 푸시를 받은 사용자가 앱에서 이달의 요금 정보를 조회
+ 푸시를 받은 사용자의 50%만 접속해도 **150만 건**을 DB에서 조회해야 함
    - 알림을 보내기 전에 요금 정보를 캐시에 적재해두면 적중률을 **99%에 가깝게** 유지할 수 있음

### 캐시 무효화
+ 캐시를 쓸 때 반드시 신경 써야 하는 점은 **유효하지 않은 데이터를 적절한 시점에 지우는 것**
    - 원본이 바뀌면 캐시도 갱신해야 함
    - 갱신하지 않으면 사용자가 잘못된 정보를 보게 됨
+ 데이터 특성에 따라 무효화 시점을 다르게 정함
+ **변경에 민감한 데이터** (가격 정보, 게시글 내용 등)
    - 변경되는 즉시 캐시를 무효화해야 함
    - 로컬 캐시가 아닌 **리모트 캐시**에 보관해야 함
        + 로컬 캐시는 자기 서버의 캐시만 바꾸고, 다른 서버의 로컬 캐시는 바꾸지 못함
        + A 서버 사용자는 변경된 가격을 보지만, B 서버 사용자는 B 서버에 남은 이전 가격을 보게 되어 서비스 신뢰성에 영향을 줌
+ **변경에 민감하지 않고 크기가 작은 데이터** (최근 인기글 목록 등)
    - 유효 시간을 설정해 주기적으로 갱신해도 좋음
    - 인기글 목록이 바뀌고 몇 분 뒤에 캐시가 갱신되어도 심각한 문제는 없음
    - 유효 시간을 10분으로 잡으면 10분마다 최신 목록으로 갱신하는 효과

### 캐시 스탬피드
+ 많이 조회되는 키의 TTL이 만료되는 순간, 그 키를 찾던 요청이 **한꺼번에 DB로 몰리는** 현상
    - 모두 캐시 미스가 나서 같은 쿼리를 동시에 실행하고, 같은 값을 동시에 캐시에 씀
    - 캐시 덕분에 버티던 트래픽이 그대로 DB에 떨어져 DB가 느려지거나 멈출 수 있음
+ 사전 적재로 많은 키를 한 번에 넣으면, TTL도 같아서 **한꺼번에 만료**되는 함정이 있음
+ 대응 방법
    - **TTL에 무작위 값을 더함** — 만료 시점을 흩어 동시에 만료되지 않게 함
    - **한 요청만 DB를 조회** — 락을 잡은 요청이 캐시를 채우고, 나머지는 잠깐 기다렸다 캐시에서 읽음
    - **만료 전에 미리 갱신** — 인기 키는 TTL이 끝나기 전에 백그라운드에서 다시 적재

### 스프링에서 캐시 쓰기
+ 스프링은 캐시 추상화를 제공해, 구현체(Caffeine, Redis 등)를 바꿔도 코드는 그대로 둘 수 있음

    ```java
    @Cacheable(cacheNames = "product", key = "#id")     // 캐시에 있으면 메서드를 실행하지 않음
    public Product getProduct(Long id) { ... }

    @CacheEvict(cacheNames = "product", key = "#product.id")   // 원본 변경 시 캐시 무효화
    public void updateProduct(Product product) { ... }
    ```

    - 설정 클래스에 `@EnableCaching`을 붙여야 동작
    - 프록시 방식이라 **같은 클래스 안에서 호출하면 캐시가 적용되지 않음**

### 자주 하는 착각
+ "캐시는 넣기만 하면 빨라진다"
    - 적중률이 낮으면 캐시 조회 비용만 더해짐. **적중률**로 효과를 확인해야 함
+ "캐시는 데이터를 넣을 때만 신경 쓰면 된다"
    - 원본이 바뀌었을 때 **언제 지울지**가 더 어려운 문제. 무효화를 놓치면 사용자가 잘못된 정보를 봄
+ "로컬 캐시가 더 빠르니 항상 낫다"
    - 서버가 여러 대면 서버마다 캐시가 따로라서 **서버별로 다른 데이터**를 보여줄 수 있음. 변경에 민감한 데이터는 리모트 캐시
+ "TTL만 걸어두면 알아서 관리된다"
    - 인기 키가 만료되는 순간 요청이 DB로 몰릴 수 있음(캐시 스탬피드). 같은 TTL로 사전 적재한 키들은 한꺼번에 만료됨
+ "`@Cacheable`만 붙이면 캐시가 적용된다"
    - `@EnableCaching`이 없거나 같은 클래스 안에서 호출하면 **조용히 캐시 없이 동작**함
