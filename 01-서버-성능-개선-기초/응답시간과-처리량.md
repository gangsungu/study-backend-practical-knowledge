## 응답시간과 처리량

성능을 이야기하려면 먼저 **무엇을 재는지**부터 정해야 한다.
서버 성능은 주로 **응답 시간**과 **처리량** 두 지표로 표현하고, 성능 개선도 이 두 숫자를 확인하는 데서 시작한다.

### 응답 시간
+ 사용자의 요청을 처리하는 데 걸리는 시간
+ 응답 시간의 구성 요소
    - API 요청 전송 시간
    - 서버의 처리 시간
    - API 응답 전송 시간 등
+ 백엔드 개발자는 주로 **서버의 처리 시간**을 확인하며, 주 구성 요소는 아래와 같음
    - 로직 수행
    - DB 연동 (SQL 실행)
    - 외부 API 연동
    - 응답 데이터 생성 (전송)

### 처리량
+ 단위 시간당 시스템이 처리하는 작업량
    - 주로 TPS(Transaction Per Second), RPS(Request Per Second)로 표현
+ 최대 TPS
    - 시스템이 **초당** 처리할 수 있는 최대 요청 수
    - 서버가 한 번에 5개의 요청을 처리할 수 있고 요청당 처리 시간이 1초라면 최대 TPS는 5

### 최대 TPS를 넘으면
+ 동시에 들어오는 요청 수가 최대 TPS를 초과하면, 초과한 요청은 **앞선 요청이 끝날 때까지 대기**한 뒤 처리됨
    - 사용자 입장에서는 대기한 만큼 응답 시간이 늘어남
+ 대기 시간을 줄이는 방법은 두 가지
    - 서버가 **동시에 처리할 수 있는 요청 수**를 늘림
    - 요청당 **처리 시간 자체**를 줄임

### 응답 시간은 백분위수로 본다
+ 평균 응답 시간은 **느린 요청을 가림**
    - 평균이 100ms여도 상위 1% 요청은 3초씩 걸릴 수 있음
    - 트래픽이 많으면 1%도 적지 않은 사용자 수
+ 그래서 모니터링에서는 **백분위수(percentile)**로 봄
    - p50 (중앙값) — 요청의 50%가 이 시간 안에 끝남
    - p95, p99 — 요청의 95%, 99%가 이 시간 안에 끝남
    - 목표 응답 시간도 "p99 500ms 이하"처럼 백분위수로 정함

### 처리량과 응답 시간의 관계
+ **동시 처리 수 = 처리량(TPS) × 응답 시간** (리틀의 법칙, Little's Law)
    - 거꾸로 쓰면 `최대 TPS = 동시 처리 수 / 응답 시간`
+ 위의 "5개 동시 처리, 요청당 1초 → 최대 TPS 5"가 바로 이 공식
    - 응답 시간을 0.5초로 줄이면 최대 TPS는 10
    - 동시 처리 수를 10으로 늘려도 최대 TPS는 10
+ 대기 시간을 줄이는 두 가지 방법이 결국 **공식의 두 항을 하나씩 건드리는 것**
+ 커넥션 풀 크기와 TPS 계산도 같은 공식 (풀 크기 5, 쿼리 0.1초 → 최대 50 TPS)

### 자주 하는 착각
+ "응답 시간 = 서버 처리 시간"
    - 사용자가 느끼는 응답 시간에는 요청·응답 **전송 시간**도 포함됨. 서버 로그의 처리 시간이 짧아도 사용자는 느리다고 느낄 수 있음
+ "평균 응답 시간이 빠르면 문제없다"
    - 평균은 느린 요청을 가림. p95·p99를 같이 봐야 함
+ "처리량이 높으면 응답 시간도 빠르다"
    - 별개의 지표. 최대 TPS 근처에서는 처리량은 유지돼도 **대기 때문에 응답 시간이 급격히 늘어남**
+ "느린 건 로직 때문이다"
    - 서버 처리 시간의 대부분은 보통 **DB 연동과 외부 API 연동**에서 나옴. 로직 최적화보다 연동 구간을 먼저 봐야 함
