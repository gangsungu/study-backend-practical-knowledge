## 가비지 컬렉터와 메모리

자바, Go, 파이썬 같은 언어는 **가비지 컬렉터(GC)**로 메모리를 관리한다.
개발자가 메모리를 직접 해제하지 않아도 되지만, GC가 도는 동안 **애플리케이션이 멈출 수 있어** 응답 시간에 영향을 준다.
그래서 서버 성능을 볼 때는 **메모리를 얼마나, 어떻게 쓰는지**도 함께 봐야 한다.

### 가비지 컬렉터의 동작
+ 사용이 끝난 객체를 힙 메모리에서 **바로 삭제하지 않음**
    - 정해진 규칙에 따라 사용하지 않는 객체를 찾아 메모리를 반환함
+ 실행 시점의 예
    - 힙 메모리 사용량이 **일정 비율을 초과**하면 실행
    - **일정 주기**로 자동 실행

### 장점과 단점
+ 장점
    - 개발자가 메모리를 직접 관리해야 하는 부담을 줄여줌
    - 코드로 메모리를 직접 다룰 수 없어 **보안 이슈**(해제한 메모리 접근 등)를 줄여줌
+ 단점
    - GC가 실행되는 동안 애플리케이션의 동작이 멈춤 — 이를 **Stop-the-world**라고 함
    - 멈추는 동안 들어온 요청은 대기하므로 **응답 시간이 길어짐**

### GC 실행 시간과 메모리
+ GC 알고리즘과 메모리 사용 패턴에 따라 차이는 있지만
    - **사용하는 메모리양과 객체 수가 많을수록** 사용하지 않는 객체를 찾는 데 오래 걸려 GC 실행 시간이 길어짐
    - 반대로 메모리 사용을 줄이면 GC 시간도 줄어듦
+ 다만 애플리케이션 실행에 **필요한 메모리보다 적게** 잡으면 실행 자체에 문제가 생김 (`OutOfMemoryError`, 잦은 GC)

### 한 번에 대량으로 객체를 만들지 않기
+ 가상 사례
    - 콘텐츠 조회 API가 한 번에 **10만 개**의 게시글을 반환할 수 있음
    - 게시글 하나가 **0.5KB**를 사용한다면 요청 하나에 약 **50MB**가 필요
    - 동시에 **100명**이 호출하면 약 **5GB(4.9GB)**가 필요
+ 요청 하나의 메모리 × 동시 요청 수만큼 메모리가 순간적으로 필요해짐
    - 힙이 순식간에 차서 GC가 자주, 오래 실행되고 최악의 경우 메모리 부족으로 서버가 죽음

### 조회 범위 제한
+ 한 번에 조회할 수 있는 범위에 **상한을 둠**
    - 10년치 내역을 한 번에 조회하기보다 **최대 6개월**처럼 기간을 제한
    - 목록 조회는 **페이징**으로 한 번에 반환하는 개수를 제한
+ 페이지 크기(`size`)를 클라이언트가 정한다면 **상한도 서버에서** 정해야 함
    - 상한이 없으면 `size=100000` 요청 하나로 10만 건이 힙에 올라감 — 페이징을 해도 대량 조회와 같아짐
    - DTO 검증이나 조회 메서드에서 최댓값을 강제함

    ```java
    public record WhiskeySearchCondition(
        Long cursor,
        @Min(1) @Max(50) int size    // 컨트롤러에서 @Valid로 검증
    ) {}

    // 또는 조회하는 쪽에서 직접 제한
    int size = Math.min(condition.size(), 50);
    query.limit(size + 1);           // +1은 다음 페이지 존재 여부 확인용
    ```

### OFFSET 페이징과 키셋 페이징
+ 두 방식 모두 `LIMIT`이 **DB 안에서** 처리되므로 애플리케이션은 한 페이지 분량만 받음 — 힙 메모리는 안전함
+ 차이는 **DB가 얼마나 읽느냐**

| | OFFSET 페이징 | 키셋(커서) 페이징 |
|---|---|---|
| 쿼리 | `ORDER BY id DESC LIMIT 20 OFFSET 99980` | `WHERE id < :lastId ORDER BY id DESC LIMIT 20` |
| 주어지는 것 | 몇 번째 행인지 (**개수**) | 어느 값부터인지 (**값**) |
| 인덱스 활용 | 정렬된 순서로 읽기만 가능 | 그 값 위치로 바로 찾아감 |
| 읽는 양 | 앞의 행 전부 + 20건 (100,000건) | 트리 높이 + 20건 |
| 특정 페이지로 이동 | 가능 | 불가능 (이전 페이지의 마지막 키가 필요) |
| 어울리는 화면 | 페이지 번호 | 무한 스크롤, 더 보기 |

+ OFFSET은 인덱스가 있어도 **앞부분을 하나씩 세면서** 넘어감
    - OFFSET은 값이 아니라 개수라서 인덱스로 찾아갈 수 없음
    - MySQL InnoDB, PostgreSQL의 B+Tree는 "이 아래에 행이 몇 개 있는지"를 저장하지 않음
+ 키셋은 B+Tree를 **루트부터 타고 내려가** 커서 값 위치를 바로 찾음 — 사전에서 단어를 찾는 것과 같음

    ```
              [루트]              ← 1. "20보다 작은 쪽은 이 자식"
             /      \
        [중간 노드]  ...          ← 2. 한 단계 더 내려감
          /    \
     [리프: ... 18, 19 | 20 ...]  ← 3. 도착. 여기서부터 역순으로 20건만 읽고 멈춤
    ```

    - 트리 높이는 수백만 건이어도 보통 3~4단계
    - 앞의 99,980건은 **아예 읽지 않음**
+ "키셋도 5000번째 페이지에 가려면 앞 페이지를 다 거쳐야 하지 않나?"
    - 키셋은 애초에 특정 페이지로 **바로 갈 수 없음**. 이전 페이지의 마지막 id가 있어야 다음 페이지를 요청할 수 있음
    - 사용자가 실제로 5000페이지까지 넘겼다면 요청이 5000번 있었던 것이고, **각 요청은 20건만** 읽음
    - OFFSET은 5000번째 요청 **한 번**에 100,000건을 읽음
+ PK라서 빠른 게 아니라 **WHERE와 ORDER BY에 맞는 인덱스**가 있어서 빠른 것
    - `whiskey_id = ? AND id < ? ORDER BY id DESC`라면 `(whiskey_id, id)` 인덱스가 필요
    - MySQL InnoDB는 보조 인덱스 끝에 PK를 자동으로 붙여 저장하므로, `whiskey_id` 단일 인덱스도 실제로는 `(whiskey_id, id)`처럼 동작
    - 맞는 인덱스가 없거나 `LIKE '%검색어%'`처럼 인덱스를 못 쓰는 조건이 있으면, 조건에 맞는 행을 찾을 때까지 훑음 — 결과가 적을수록 **많이 읽음**

### JPA 컬렉션 fetch join과 페이징
+ 컬렉션(`@OneToMany`)을 fetch join하면서 페이징하면 Hibernate가 **전체를 메모리에 올린 뒤 잘라냄**
    - `HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory` 경고가 남
    - 페이징을 걸었는데도 10만 건이 힙에 올라가는 상황
+ 원인은 **조인하면 행이 불어나기** 때문
    - 게시글 1건에 댓글이 10개면 조인 결과는 10행
    - SQL에 `LIMIT 20`을 걸면 "게시글 20건"이 아니라 "조인된 행 20개"가 잘림
    - 그래서 Hibernate는 SQL에 LIMIT을 붙이지 않고 메모리에서 자름
+ **QueryDSL로 바꿔도 해결되지 않음**
    - QueryDSL은 JPQL을 만들어주는 도구일 뿐이라 `.fetchJoin()` + `.offset().limit()`도 똑같이 동작함
    - 네이티브 쿼리로 직접 LIMIT을 걸 수는 있지만, 행이 불어나는 문제는 그대로이고 엔티티·컬렉션 매핑도 직접 해야 함
+ 해결 방법 1 — **컬렉션은 fetch join하지 않고 배치 사이즈로 가져오기** (가장 많이 씀)

    ```yaml
    spring.jpa.properties.hibernate.default_batch_fetch_size: 100
    ```

    - 게시글만 페이징해서 조회 (ToOne 관계는 행이 불어나지 않으므로 fetch join해도 됨)
    - 댓글에 접근할 때 `WHERE post_id IN (...)`으로 최대 100건씩 묶어 조회
    - 쿼리가 1 + 1번 수준으로 끝나 N+1 문제도 생기지 않음
    - 특정 연관관계에만 적용하려면 `@BatchSize`
+ 해결 방법 2 — **ID만 먼저 페이징하고, 그 ID로 fetch join하기**

    ```java
    // 1) 게시글 ID만 페이징 — 행이 불어나지 않으므로 DB에서 정확히 잘림
    List<Long> ids = em.createQuery("SELECT p.id FROM Post p ORDER BY p.id DESC", Long.class)
            .setFirstResult(0)
            .setMaxResults(20)
            .getResultList();

    // 2) 해당 ID만 컬렉션과 함께 조회
    List<Post> posts = em.createQuery(
            "SELECT DISTINCT p FROM Post p JOIN FETCH p.comments WHERE p.id IN :ids ORDER BY p.id DESC", Post.class)
            .setParameter("ids", ids)
            .getResultList();
    ```

+ Hibernate 6에서는 이 상황을 경고 대신 **예외로** 바꿀 수 있음 — 실수를 바로 잡아낼 수 있어 켜두는 것을 추천

    ```yaml
    spring.jpa.properties.hibernate.query.fail_on_pagination_over_collection_fetch: true
    ```

### 스트림 활용
+ 파일 다운로드처럼 큰 데이터를 다루는 기능은 전체를 메모리에 올리지 말고 **스트림**으로 조금씩 읽고 씀
+ 스트림을 사용하지 않는 경우

    ```java
    byte[] bytes = Files.readAllBytes(Path.of("path")); // 파일 전체를 한 번에 메모리에 로딩
    out.write(bytes);

    // 다운로드 파일이 10MB라고 가정하면, 100명이 동시에 다운로드할 때 1GB의 메모리가 필요
    ```

+ 스트림을 사용하는 경우

    ```java
    try (InputStream is = Files.newInputStream(Path.of("path"))) {
        byte[] buffer = new byte[8192];  // 8KB씩 읽고 씀
        int read;
        while ((read = is.read(buffer, 0, 8192)) >= 0) {
            out.write(buffer, 0, read);
        }
    }

    // 요청 하나가 쓰는 메모리는 버퍼 크기(8KB)뿐. 100명이 동시에 다운로드해도 약 800KB
    ```

    - 자바 9부터는 `is.transferTo(out)` 한 줄로 같은 동작을 할 수 있음
    - 스트림은 반드시 닫아야 하므로 **try-with-resources**로 감쌈

### 자주 하는 착각
+ "GC가 있으니 메모리는 신경 쓰지 않아도 된다"
    - GC는 해제를 대신해줄 뿐, **얼마나 쓰는지**는 코드가 정함. 많이 쓸수록 GC가 오래 멈춤
+ "메모리를 넉넉히 주면 GC 문제는 해결된다"
    - 힙이 클수록 한 번에 정리할 대상이 많아져 **한 번의 GC가 더 오래 걸릴 수 있음**
+ "요청 하나에 50MB면 별문제 없다"
    - 메모리는 **동시 요청 수만큼 곱해짐**. 트래픽이 몰리는 순간을 기준으로 계산해야 함
+ "페이징을 하면 전체를 조회한 뒤 잘라내는 것이다"
    - `LIMIT`/`OFFSET`은 **DB 안에서** 처리됨. 애플리케이션은 한 페이지 분량만 받으므로 힙 메모리는 안전함
    - 다만 OFFSET이 크면 DB가 앞의 행을 **모두 읽고 버리므로** 뒤 페이지일수록 느려짐 ([OFFSET 페이징과 키셋 페이징](#offset-페이징과-키셋-페이징) 참고)
    - 진짜로 전체를 메모리에 올리는 경우는 **애플리케이션에서 페이징**할 때
        + 전체를 `List`로 가져와 `subList()`로 자르는 코드
        + JPA에서 **컬렉션 fetch join과 페이징을 함께** 쓰는 경우 — Hibernate가 SQL에 LIMIT을 붙이지 못하고 전체를 메모리에 올린 뒤 잘라냄 ([JPA 컬렉션 fetch join과 페이징](#jpa-컬렉션-fetch-join과-페이징) 참고)
+ "커서 기반 페이징이니 안전하다"
    - 커서는 OFFSET 비용만 없애줌. `size`에 **상한이 없으면** 한 번에 얼마든지 조회할 수 있음
    - 커서 조건에 맞는 **인덱스가 없으면** 키셋이어도 많이 읽음
    - 컬렉션을 fetch join하면 커서 방식이어도 전체를 메모리에 올린 뒤 잘라냄
+ "파일은 읽어서 보내면 된다"
    - `readAllBytes`는 파일 크기만큼 메모리를 씀. 큰 파일은 **스트림**으로 보내야 함
