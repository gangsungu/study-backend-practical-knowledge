## 병목지점과 서버 확장

성능 개선은 느리다고 이것저것 시도해보는 일이 아니다.
**현재 서버의 TPS와 응답 시간을 먼저 확인**하고, 그 결과를 바탕으로 목표 TPS와 응답 시간을 정한 뒤에 손을 대야 한다.
여기서는 트래픽이 늘 때 성능 문제가 왜 생기는지, 서버를 늘리는 두 가지 방법과 각각의 한계를 정리한다.

### 성능 개선의 시작
+ 막연히 시도하지 않고 **측정 → 목표 설정 → 개선** 순서로 진행
    - 현재 서버의 TPS와 응답 시간 확인
    - 결과를 바탕으로 목표 TPS와 응답 시간 설정

### 병목지점
+ 서비스 초기에는 문제가 잘 생기지 않다가, 사용자가 늘어 **트래픽이 늘고 데이터가 쌓이면서** 성능 문제가 생기기 시작함
+ 주된 이유는 시스템이 수용할 수 있는 **최대 TPS를 초과하는 트래픽**이 유입되기 때문
    - 최대 TPS를 늘리지 않으면 증가하는 트래픽을 적절히 처리할 수 없음
+ TPS를 높이려면 먼저 **성능 문제가 발생하는 지점**을 찾아야 함
    - 주로 **DB**나 **외부 API**를 연동하는 과정에서 발생

### 수직 확장
+ 서버 자체의 성능(CPU, 메모리 등)을 높이는 방법
+ 가장 빠르게 문제를 해결할 수 있고 효과가 즉각적
+ 한계
    - 트래픽이 계속 증가하면 언젠가 성능 문제가 다시 발생
    - 비용이 많이 들어 그때마다 반복할 수 없음

### 수평 확장
+ 서버를 추가로 투입해 TPS를 높이는 방법
+ **무턱대고 서버를 추가하면 안 됨**
    - DB에서 성능 문제가 발생하는 상황에서 서버를 추가하면, 요청이 늘어난 만큼 DB 연결도 늘어나 문제가 더 커짐
    - 서버를 늘리기 전에 병목이 어디인지부터 확인해야 하는 이유

#### 서버를 늘리면 DB 커넥션은 몇 개가 되나
+ 서버마다 커넥션 풀을 따로 가지므로, DB가 받는 커넥션 수는 **서버 수 × 풀 크기**
    - 풀 크기 20인 서버를 2대에서 10대로 늘리면 DB 커넥션은 40개 → 200개
+ 이 값이 DB의 최대 연결 수(MySQL `max_connections` 등)를 넘으면 **새 연결 자체가 실패**
+ 넘지 않더라도 동시에 실행되는 쿼리가 늘어 DB CPU·락 경합이 커지고, 쿼리 실행 시간이 길어짐
    - 서버를 늘렸는데 오히려 느려지는 이유
+ 수평 확장을 계획할 때는 **서버 수와 풀 크기를 함께** 정해야 함

| 구분 | 수직 확장 | 수평 확장 |
|------|----------|----------|
| 방법 | 서버 성능을 높임 | 서버 수를 늘림 |
| 장점 | 즉각적인 효과 | 트래픽 증가에 맞춰 서버를 더 투입할 수 있음 |
| 주의할 점 | 비용이 커서 계속 반복할 수 없음 | 병목이 DB라면 오히려 문제가 커짐 |

### 자주 하는 착각
+ "느리면 일단 고쳐보면 된다"
    - 현재 TPS와 응답 시간을 모르면 개선됐는지조차 판단할 수 없음. **측정이 먼저**
+ "서버를 늘리면 무조건 빨라진다"
    - 병목이 DB라면 서버를 늘릴수록 DB 커넥션과 동시 쿼리가 늘어 **오히려 느려짐**
+ "수직 확장으로 계속 버틸 수 있다"
    - 효과는 즉각적이지만 비용이 크고 한계가 있음. 트래픽이 계속 늘면 다시 문제가 생김
+ "서비스 초기에 문제가 없었으니 구조도 괜찮다"
    - 성능 문제는 **트래픽이 늘고 데이터가 쌓이면서** 드러남. 초기의 문제없음은 부하가 적어서일 수 있음
